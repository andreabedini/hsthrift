# Building with Buck2

Work in progress: building hsthrift with [Buck2](https://buck2.build). So
far this covers the C++ dependencies that `new_install_deps.sh` builds with
getdeps, the Haskell toolchains, and some of the Haskell packages (see "The
Haskell packages"); the others still build with cabal.

buck2 itself, buildifier and yq are in `mise.toml`, at the versions
[timbuktu](https://github.com/andreabedini/timbuktu) uses (its rules need
the prelude bundled with that buck2):

    mise install

## The C++ dependencies

Each dependency has a BUCK file in `deps/<name>/`, written by
`generate.py` from its getdeps manifest (in `build/fbcode_builder/manifests`,
or in `manifests/` for the ones getdeps does not have). It holds:

- `<name>-src`: an `http_archive` of the pinned source;
- `<name>-build`: a `getdeps_project` (`project.bzl`), one action that runs
  the project's CMake or configure/make build and installs it into a
  prefix;
- `<name>`: a `prebuilt_cxx_library` of what was installed, to depend on.

Libraries are static and position-independent. Dependencies that getdeps
takes from the distribution are in `deps/system/BUCK`, as linker flags.

Build them and run programs using folly and fbthrift (which pulls in
wangle, fizz and mvfst):

    buck2 build //build/buck/deps/fbthrift:fbthrift
    buck2 test //build/buck/tests/...

These are big builds. Each `getdeps_project` action takes all of Buck2's
local slots, so only one runs at a time, and runs as many jobs as half the
memory available allows for the manifest's `job_weight_mib`; each of its
processes is limited to ten times that much virtual memory (see
`build_project.py`). A cap on everything the daemon runs is better still,
with Buck2's resource control (systemd) in `.buckconfig.local`:

    [buck2_resource_control]
      status = if_available
      memory_max = 17179869184

The builds use the compilers, cmake and ninja in `PATH`, and system
packages for the dependencies in `deps/system/BUCK`. On Fedora these are
`boost-devel`, `glog-devel`, `gflags-devel`, `libevent-devel`,
`libsodium-devel`, `libdwarf-devel`, `libunwind-devel`, `lz4-devel`,
`snappy-devel`, `libzstd-devel`, `xz-devel`, `openssl-devel` and zlib.

## Regenerating

After changing a manifest, a revision in `build/deps/github_hashes` or
`generate.py`:

    python3 build/buck/generate.py

Revisions of git manifests that `github_hashes` does not pin (fizz, wangle,
mvfst) are pinned in `deps/sources.json` the first time, with the sha256 of
every GitHub archive. Delete an entry to update it.

## Differences from getdeps

- liburing is built from source: folly uses it whenever `<liburing.h>`
  exists, and needs 2.15 or later (see `manifests/liburing`).
- Static rather than shared libraries (`build.sh` asks getdeps for shared
  ones). Where a project installs an archive for each component and none
  with all of them (fbthrift), they are merged into one
  (`merge_archives.py`), so that linking needs no order among them; the C++
  toolchain orders the libraries topologically.
- A manifest's default features are on, as in getdeps, except fbthrift's
  `benchmark` (`FEATURES_OFF` in `generate.py`).
- folly's system libraries include zlib and bzip2, which it links when
  CMake finds them although its manifest lists them on Windows only.

## The Haskell rules and toolchains

The Haskell rules are timbuktu's, a git external cell pinned to a commit in
`.buckconfig` (`[external_cell_timbuktu]`). The cell has to be called
`timbuktu`: that is how the rules refer to themselves. To use a newer
timbuktu, change `commit_hash`.

The toolchains are in `toolchains/BUCK`. `toolchains//:haskell`, the GHC
of every Haskell rule, is GHC 9.6.7 for the packages and their build
tools (hsthrift needs ghc < 9.9) and 9.12.2 for timbuktu's own helpers,
which need Cabal 3.12 or later. The GHC and cabal-install distributions are pinned in
`toolchains/ghcup/BUCK`, which is generated; to pin another version:

    buck2 bxl timbuktu//rules/haskell/ghcup/ghcup.bxl:pin -- --ghc 9.8.4

and copy the file it prints to `build/buck/toolchains/ghcup/BUCK` (the
versions already there are kept). It needs curl and yq.

timbuktu's own examples build from here (`buck2 test
timbuktu//examples/cabal_simple/hello:hello-test` passes), but a test whose
program is a file of the external cell cannot start: Buck2 runs it in the
directory of the cell, `build/buck/timbuktu`, which does not exist.

## The Haskell packages

The `BUCK` file at the root of the repository is a build plan, generated by
timbuktu's `plan.bxl` (its header says how to make it again): the packages
from Hackage, built by their `Setup.hs`, and the packages of this
repository given with `--local-package`, as `cabal_simple` targets whose
sources are globs of their directories. It plans with GHC 9.6.7 and the
Hackage index as of 2025-04-14, as Glean pins it. `plan.bxl` needs
cabal-solver-plan, whose path goes in `.buckconfig.local`:

    [haskell]
      cabal_solver_plan = /path/to/cabal-solver-plan

The C and C++ libraries a package names in `pkgconfig-depends` are Buck2
targets, given to `plan.bxl` as `--pkgconfig NAME=TARGET`: the libraries of
`build/buck/deps`. pkg-config is not run. The solver takes each NAME as
installed, and the package's targets get TARGET in `cxx_deps`; their
headers reach whatever depends on the package too, as with Cabal.

folly comes from `build/buck/deps/folly`, through `folly-clib` with
`-bundled-folly`: there `folly-clib.cabal` is only `pkgconfig-depends:
libfolly`. That file is not in the repository (the Makefile makes it from
`folly-clib.cabal.in`), and `plan.bxl` needs it; before planning, run

    make setup-folly-buck

So far the plan has `fb-stubs`, `mangle`, `folly-clib`, `fb-util` (with
`+folly`) and `thrift-compiler`:

    buck2 run //:exe-mangle -- "int foo(int, char const*)"
    buck2 build //:fb-util
    buck2 run //:exe-thrift-compiler -- --hs $PWD/lib/if/RpcOptions.thrift -o /tmp/out
